# Migrating from DoveWAI Protocol v0.1 to v0.2

v0.2 is the recommended version for new implementations. v0.1 remains frozen and valid for compatibility.

## Rule: never silently reinterpret versions

A v0.1 envelope is not a v0.2 envelope. Converters MUST explicitly create a v0.2 object and SHOULD preserve source identifiers through direct fields or namespaced migration metadata where appropriate.

## Object mapping

| v0.1 | v0.2 | Notes |
|---|---|---|
| Task | Task | Add `idempotency_key` when the application has retry/deduplication semantics. |
| Capability | Capability | Existing semantics continue; structured negotiation may be added by profiles. |
| Claim | Claim | Add lease generation/fencing metadata when distributed write ownership needs stale-writer protection. |
| ExecutionEvent | ExecutionEvent | Prefer `attempt_id`; causal and timing fields are available. |
| Provenance | Provenance / Artifact evidence | Use Artifact for durable outputs and independently addressable evidence. |
| Result | Result | v0.2 Result is terminal only. |
| ProtocolError | ProtocolError | Existing structured-error concept continues. |

New v0.2 objects:

- `Attempt`
- `Artifact`
- `Verification`
- `WorkReceipt`

## Partial results

v0.1 allowed `Result.status = partial`. v0.2 deliberately removes that terminal status.

When converting a non-terminal partial output, represent it as an `ExecutionEvent`, checkpoint, or `Artifact`. Create the v0.2 `Result` only when the task reaches `succeeded`, `failed`, or `cancelled`.

If a historical v0.1 `partial` Result was intended as the final outcome, a converter MUST NOT guess a v0.2 terminal status. It SHOULD require application-specific policy or record the historical object as evidence and leave conversion indeterminate.

## Attempts

v0.1 executions that contain retries SHOULD be split into explicit v0.2 Attempts whenever the source data makes individual retries distinguishable. A converter MUST NOT invent precise attempt boundaries that cannot be supported by source evidence.

## Verification and receipts

Migration does not automatically make historical work verified.

A converter MAY create a `WorkReceipt` with status `recorded` when it can reliably link the historical Task and terminal Result. It MUST NOT create receipt status `verified` unless one or more v0.2 Verification objects actually support that status.

## Recommended adoption behavior

- New integrations: emit v0.2 directly.
- Existing v0.1 integrations: continue validating v0.1 until explicitly upgraded.
- Mixed systems: route by `protocol_version` before schema or lifecycle interpretation.
- Gateways: expose conversion as an explicit operation and report lossy mappings.
